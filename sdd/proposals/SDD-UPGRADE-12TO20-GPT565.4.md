# SDD系统 12.6/24 → 20+/24 升级可执行方案

## 目标

在一个可控周期内，把 SDD 系统总评分从 `12.6/24` 提升到 `20+/24`。  
策略不是平均发力，而是按分值杠杆、依赖关系、落地难度三者排序，优先拿下高收益项，并把 7 个系统纳入统一治理。

## 总体原则

1. 先补“评分增益最大且互相依赖强”的能力：`CI门禁`、`部署覆盖`、`自动化闭环`、`多模型投票`、`AI修复稳定率数据`。
2. 覆盖率不追求一次全仓 80%，按系统分层推进：先把低覆盖核心系统拉到可用线，再做全局提分。
3. Spec 不做文档运动，必须与测试、门禁、部署、运行记录直接挂钩。
4. 所有验收都要求“有数据、有流水线记录、有样例仓库/系统证明”。

- 核心系统至少 3 个具备 `prod/prod-like` 验证

## P0-3：自动化闭环 `(+0.7)`

### 目标
把“Spec → 开发 → 测试 → 修复 → 部署 → 记录”的链条打通。

### 工作项
1. 建立任务状态机
   - spec ready
   - implementation ready
   - tests failed
   - ai repair running
   - validated
   - deploy ready
   - deployed

2. 打通触发链
   - Spec 更新触发测试映射校验
   - PR 触发 CI
   - CI 失败触发 AI 修复流程
   - 修复完成自动回归
   - 通过后触发部署与 smoke

3. 打通证据沉淀
   - 日志
   - 修复 diff
   - 测试报告
   - 部署记录
   - 运行快照

### 验收标准
- 至少 3 个系统实现端到端闭环
- 至少 20 个真实任务可回溯完整链路
- 能按任务 ID 查到 Spec、代码、测试、部署、记录

## 第3阶段：冲击 20+ 分的关键增益（第5-8周）

## P1-1：AI 修复从单次成功到稳定率数据 `(+1.0)`

### 目标
证明 AI 修复不是个案，而是稳定系统能力。

### 工作项
1. 设计 AI 修复评测集
   - 单测失败

   - 类型错误
   - 接口契约不匹配
   - 前端构建失败

- 至少 100 个修复样本

## P1-2：多模型投票从“阵容”到“有效系统” `(+1.2)`

### 目标
不再只是并列调用多个模型，而是形成可证明优于单模型的决策机制。

### 工作项
1. 设计投票架构
   - 候选生成
   - 规则过滤
   - 测试验证
   - 结果排序
   - 最终选择

2. 定义模型角色
   - 生成模型
   - 审查模型
   - 风险模型
   - 成本控制模型

3. 引入真实评分信号
   - 测试通过率
   - diff 规模
   - 变更风险
   - 历史成功率
   - 修复耗时

4. 对比单模型基线
   - 单模型 A
   - 单模型 B
   - 多模型投票系统

### 验收标准
- 在同一评测集上，多模型系统较单模型提升明确
- 至少在 `成功率` 或 `新故障率` 上有统计显著改善
- 有失败样本复盘机制
- 可输出每次投票决策链路和最终依据

### 验收标准
- 全局平均覆盖率达到 80%，或按审计口径达到目标分
- 低于 60% 的系统清零
- 核心业务路径都有自动化回归

## 结论

这次升级不能按“补测试”单线推进，必须按“门禁 + 部署 + 闭环 + 数据证明”来组织。  
实际执行上，前 4 周先完成工程化底座和统一验收，后 4 周集中做 AI 修复、多模型投票和覆盖率冲分，最后 2 周补生产可信度和数据集验证。这样路径最短，且最接近 `20+/24` 的确定性交付。

我可以下一步继续补两份直接可用的产物：
1. `10周项目排期表（按周/负责人/依赖）`
2. `升级验收清单模板（可直接给团队执行）`
