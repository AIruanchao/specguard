## 按实施顺序合并后的最短路径

| 阶段 | 目标 | 必须完成的验收证据 |
|---|---|---|
| 第 1 阶段 | 让门禁真实阻断 | ERP runner 在线证明、required checks 配置、负向 PR 失败记录、override 审计、coverage gate |
| 第 2 阶段 | 建立可复现和可追踪基础 | 干净环境部署日志、immutable artifact、rollback 演练、run ID、spec/需求/测试映射 |
| 第 3 阶段 | 把自报指标变成可审计指标 | SpecGuard 标注集、逆向引擎冻结测试集、AI patch acceptance 定义、模型盲测报告 |
| 第 4 阶段 | 生产化自动化闭环 | 状态机、幂等重试、DLQ、告警 SLA、人工接管、shadow/canary、审计产物 |
| 第 5 阶段 | 达到长期满分可信度 | 漂移检测、mutation/branch coverage、灾备恢复、迁移演练、规则/模型版本回归、缺陷逃逸指标 |

## 当前最重要的结论

1. **最高风险不是“有没有功能”，而是“失败时是否不可绕过”。**  
   CI、零欠项、coverage 和部署必须先做负向测试。只展示成功运行不能证明门禁有效。

2. **19% 和 83% 目前都不能作为可计分的生产指标。**  
   在没有冻结数据集、标签规范、盲测、分层指标和置信区间前，它们最多是实验观测值。

3. **Spec 完成率需要从状态统计升级为证据链统计。**  
   一个 `approved` spec 不能自动证明实现完成；必须关联代码、测试结果、部署版本和验证结论。

4. **AI 修复和多模型投票的核心缺口不是模型数量，而是拒答、回归、安全和人工接管。**  
   对高风险修复，安全的“拒绝自动修改”应被视为有效结果，而不是失败。

5. **覆盖率必须从“测试数量”升级为“可验证的测试质量”。**  
   至少需要 line、branch、关键路径、ERP、故障场景和报告完整性；长期还需要 mutation、flaky rate 和缺陷逃逸率。

按投入产出比，第一批应实施 `P0-01` 至 `P0-15`。这批完成后，系统才具备重新测量其余 8 个维度的可信基础；否则继续增加规则、模型或定时任务，分数会增长，但审计可信度不会同步增长。
