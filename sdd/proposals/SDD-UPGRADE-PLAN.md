# SDD 天花板升级迭代方案

## 1. 目标与总体判断

### 1.1 当前成熟度

当前整体成熟度为 `5.3/10`，已经完成“SDD 全系统部署”，但尚未形成统一、可持续、可量化的工程闭环。

当前主要问题不是缺少 SDD 文件，而是：

- SDD 覆盖率、质量、变更追踪标准不统一
- CI 只在少数系统生效，无法形成强制约束
- 零欠项检查未成为统一门禁
- 股票仪表盘、台账质量系统的 `spec.md` 仍处于骨架级 Draft
- SpecGuard 尚未真正接入项目运行数据
- 多模型评审尚未成为 SDD 生命周期的一部分
- 缺少跨系统的指标、版本、审计和责任归属

### 1.2 数据口径问题

现有状态表存在两个需要在 P0 立即修复的数据不一致：

1. 标称“7 个系统”，表格中实际列出 6 个系统
2. 标称“5/7 系统未测”，但表中商务单据、SpecGuard、DH 企业工厂均存在覆盖率数据，即至少 3 个系统已测

因此，第一阶段必须先建立统一的系统资产清单和指标计算口径，否则后续的覆盖率、成熟度和验收数据不可比较。

### 1.3 终态目标：成熟度 9/10

| 能力域 | 当前估计 | 9/10 目标 |
|---|---:|---:|
| SDD 覆盖率 | 低于 45% 的系统较多 | 所有系统 ≥ 80%，核心模块 ≥ 95% |
| spec.md 质量 | 部分为 Draft/骨架 | 所有生产模块达到 A/B 级，禁止骨架级文档进入主干 |
| CI 门禁 | 2/7 | 7/7，所有主干和 PR 强制执行 |
| 零欠项门禁 | 1/7 | 7/7，PR 和定时任务均执行 |
| 变更追踪 | 不统一 | 需求、代码、测试、发布记录可双向追踪 |
| 自动修复 | 基础检查为主 | 自动生成缺口、报告、修复建议和任务 |
| 多模型评审 | 未集成 | 高风险变更必须完成多模型投票 |
| 可观测性 | 分散 | 统一仪表盘、趋势、告警和审计记录 |
| 线上反馈闭环 | 不完整 | 线上缺陷可回溯至 spec、提交、测试和责任人 |

成熟度评分建议采用 10 个能力域，每个能力域 0～10 分，最终取加权平均：

- 规范完整性：15%
- spec.md 质量：15%
- 代码覆盖率：10%
- 测试覆盖率：10%
- CI 门禁：10%
- 零欠项治理：10%
- 变更追踪：10%
- 自动化程度：10%
- 多模型评审：5%
- 运行反馈闭环：5%

# 2. 分阶段路线图

## P0：基线校准与门禁统一

**周期：第 1～2 周**

**目标：从“状态不可完全确认”进入“指标可信、规则统一、所有系统可检查”。**

### 关键工作

1. 建立 7 个系统的正式资产清单：
   - 系统名称、代码仓库、默认分支
   - SDD 根目录
   - spec.md 数量和等级
   - 模块清单
   - CI 配置
   - 责任团队和负责人
2. 统一覆盖率计算公式：
   ```text
   SDD覆盖率 = 已有有效spec且能映射到代码模块的模块数 / 生产模块总数
   ```
3. 明确定义 spec 质量等级：
   - A：完整、可执行、可验证、包含异常和边界条件
   - B：主流程完整，但存在少量非关键缺口
   - C：信息不完整，不能作为实现依据
   - Draft：仅有结构或待补充内容
4. 统一零欠项规则：
   - 不允许无 owner 的欠项
   - 不允许无截止日期的欠项
   - 不允许过期欠项
   - 不允许高风险欠项直接进入主干
5. 为所有系统提供统一 GitHub Actions 模板
6. 建立统一 `sdd-manifest.yaml`：
   ```yaml
   system: example
   sdd_version: "2.0"
   spec_roots:
     - docs/specs
   source_roots:
     - src
   test_roots:
     - tests
   coverage_target: 0.80
   zero_debt_gate: true
   risk_review:
     required_level: high
   ```
7. 修复“7 个系统”和“5/7 未测”的统计口径问题

### P0 里程碑

- `M0.1`：7 个系统全部完成资产登记
- `M0.2`：所有系统均可生成覆盖率报告
- `M0.3`：所有系统均可执行零欠项检查
- `M0.4`：统一 CI 模板通过至少 3 个试点系统验证
- `M0.5`：形成第一版全系统基线报告

## P1：全系统工程化接入

**周期：第 3～6 周**

**目标：7/7 系统具备可运行的 CI 门禁和零欠项门禁。**

### 统一 CI 流程

每个 Pull Request 至少执行以下步骤：

```text
检出代码
  ↓
解析 sdd-manifest.yaml
  ↓
spec 格式和结构检查
  ↓
spec 与代码模块映射检查
  ↓
spec 与测试映射检查
  ↓
覆盖率计算
  ↓
零欠项检查
  ↓
变更风险评估
  ↓
高风险变更多模型评审
  ↓
生成 PR 报告
  ↓
通过/阻断合并
```

### P1 强制门槛

| 检查项 | P1 门槛 |
|---|---:|
| spec 结构合法率 | 100% |
| 主干代码的有效 spec 覆盖率 | ≥ 60% |
| 核心模块覆盖率 | ≥ 80% |
| spec 到代码映射成功率 | ≥ 90% |
| spec 到测试映射成功率 | ≥ 70% |
| 过期零欠项 | 0 |
| 高风险未评审变更 | 0 |
| CI 成功率 | ≥ 95% |
| CI 平均执行时间 | ≤ 10 分钟 |

### P1 里程碑

- `M1.1`：7/7 仓库接入统一 GitHub Actions
- `M1.2`：7/7 仓库具备零欠项门禁
- `M1.3`：每个 PR 自动生成 SDD 检查报告
- `M1.4`：所有主干分支启用 Branch Protection
- `M1.5`：连续 2 周无绕过门禁的合并记录

---

## P2：质量提升与智能评审

**周期：第 7～11 周**

**目标：从“能检查”提升到“能判断质量、识别风险、辅助修复”。**

### 重点建设

1. 补齐股票仪表盘、台账质量系统的生产级 `spec.md`
2. 商务单据系统从 45% 提升至 80%
3. DH 企业工厂从 32% 提升至 80%
4. ERP 完成 glob 匹配 95% 的实测验证
5. SpecGuard Web UI 接入真实仓库和真实检查结果
6. 引入多模型投票：
   - 规则模型：结构、字段、链接、映射
   - 语义模型：需求完整性、异常场景、边界条件
   - 风险模型：数据安全、兼容性、回滚和高风险变更
7. 生成自动化缺口任务：
   - 缺失 spec
   - 缺失测试
   - 失效链接
   - 未覆盖异常分支
   - 无 owner 的欠项
8. 引入 spec 版本和迁移机制，禁止无说明的破坏性修改

### 多模型投票规则

高风险变更至少满足：

```text
规则检查通过
AND
至少 2/3 模型通过
AND
没有 P0/P1 风险项
AND
人工 reviewer 批准
```

投票结果必须持久化，包含：

- 模型版本
- 输入 spec 版本
- 输入代码提交 SHA
- 评审时间
- 投票结论
- 发现的问题
- 人工最终决策

### P2 里程碑

- `M2.1`：商务单据系统覆盖率达到 80%
- `M2.2`：DH 企业工厂覆盖率达到 80%
- `M2.3`：股票和台账所有生产模块达到 B 级以上
- `M2.4`：ERP glob 匹配实测准确率达到 ≥ 95%
- `M2.5`：SpecGuard Web UI 接入至少 4 个真实系统
- `M2.6`：高风险 PR 的多模型评审成功率达到 100%

---

## P3：持续治理与 9/10 达标

**周期：第 12～16 周**

**目标：形成可持续运营的 SDD 平台和质量治理体系。**

### 重点建设

1. 建设统一 SDD Dashboard：
   - 系统成熟度
   - 覆盖率趋势
   - spec 质量分布
   - 欠项数量和年龄
   - CI 成功率
   - 高风险变更
   - 多模型评审结果
   - 线上缺陷回溯率
2. 建立每周质量报告和月度治理会议
3. 建立版本化基线：
   - 每次发布冻结 SDD 基线
   - 记录代码、spec、测试、发布版本之间的关系
4. 建立线上问题回灌机制：
   - 线上缺陷必须关联到 spec
   - 若 spec 未描述场景，自动创建补充任务
   - 修复必须补充测试
5. 建立 SDD 变更委员会或轻量评审机制：
   - 普通变更由团队自审
   - 高风险变更由架构负责人和业务负责人共同审批
6. 对规则、模型和模板进行版本化管理
7. 进行季度级成熟度复评

### P3 里程碑

- `M3.1`：7/7 系统覆盖率达到 ≥ 80%
- `M3.2`：核心模块覆盖率达到 ≥ 95%
- `M3.3`：7/7 系统 CI、零欠项、风险门禁全部生效
- `M3.4`：线上缺陷回溯到 spec 的比例 ≥ 90%
- `M3.5`：高风险变更评审留痕率 100%
- `M3.6`：全系统成熟度达到 ≥ 9.0/10
- `M3.7`：连续 4 周无关键门禁回退

# 4. 自动化闭环设计

## 4.1 SDD 生命周期

```text
需求提出
  ↓
生成/修改 spec
  ↓
规则校验
  ↓
代码与测试实现
  ↓
自动映射
  ↓
覆盖率和零欠项检查
  ↓
风险分级
  ↓
多模型投票
  ↓
人工审批
  ↓
合并与发布
  ↓
线上指标和缺陷回灌
  ↓
更新 spec 与测试
```

## 4.2 统一数据模型

每一个 spec 必须包含：

```yaml
id: SPEC-ERP-001
title: 订单审批
status: active
owner: team-erp
reviewers:
  - architect
version: 1.2.0
risk_level: high
source_modules:
  - src/order/approval
test_modules:
  - tests/order/approval
acceptance:
  - approval must be idempotent
debt:
  - id: DEBT-001
    owner: team-erp
    due: 2026-09-15
    severity: medium
```

核心实体包括：

- `System`
- `Spec`
- `Module`
- `Test`
- `Change`
- `Debt`
- `Review`
- `Release`
- `Incident`

## 4.3 自动化任务分工

### PR 阶段

必须完成：

- YAML/Markdown 结构校验
- spec ID 唯一性检查
- 链接和引用检查
- spec 与代码目录匹配
- spec 与测试匹配
- 变更影响分析
- 覆盖率变化检查
- 欠项检查
- 风险分级
- 必要时触发多模型评审

### 定时阶段

建议每天执行：

- 全量覆盖率扫描
- 过期欠项扫描
- 失效链接扫描
- 未关联代码模块扫描
- spec 与代码漂移检测
- 模型评审结果复核

建议每周执行：

- 生成系统成熟度报告
- 对覆盖率下降超过 `5 个百分点` 的系统告警
- 对新增 P0/P1 欠项告警
- 统计 CI 失败原因
- 输出治理任务排行榜

### 发布阶段

发布必须生成：

- SDD 基线版本
- 代码提交 SHA
- 测试报告
- 多模型评审结果
- 未关闭欠项清单
- 风险接受记录
- 回滚方案

## 4.4 门禁分级

| 风险等级 | 示例 | 处理要求 |
|---|---|---|
| Low | 文案、非核心页面样式 | 规则检查通过即可 |
| Medium | 普通业务字段和流程调整 | 规则检查 + 1 名 reviewer |
| High | 状态机、资金、权限、数据结构、外部接口 | 多模型投票 + 架构/业务双审 |
| Critical | 数据迁移、核心交易、生产安全 | 多模型投票 + 灰度发布 + 回滚演练 |

# 5. 验收标准

## 5.1 全局验收

达到以下条件才可宣称 SDD 体系升级完成：

- 资产清单中系统数量、仓库和负责人准确率 `100%`
- 7/7 系统接入统一 CI
- 7/7 系统启用零欠项门禁
- 7/7 系统覆盖率可重复计算
- 7/7 系统覆盖率 `≥ 80%`
- 核心模块覆盖率 `≥ 95%`
- 生产模块不存在 Draft 或骨架级 spec
- spec 到代码映射成功率 `≥ 95%`
- spec 到测试映射成功率 `≥ 90%`
- P0/P1 欠项数量为 `0`
- 过期欠项数量为 `0`
- 高风险变更评审留痕率 `100%`
- 线上缺陷回溯到 spec 的比例 `≥ 90%`
- 主干 CI 成功率 `≥ 98%`
- 连续 4 周无绕过门禁合并
- 全系统成熟度评分 `≥ 9.0/10`

## 5.2 SpecGuard 验收

- Web UI 接入至少 6 个真实系统
- 能查看系统、模块、spec、欠项、覆盖率和趋势
- 报告生成时间不超过 `60 秒`
- 规则检查结果可定位到文件和行号
- 同一提交重复执行结果一致
- 支持历史版本对比
- 支持导出 Markdown 和 JSON 报告

## 5.3 多模型评审验收

- 高风险变更触发率 `100%`
- 每次评审记录模型版本、输入版本和结论
- 模型调用失败时自动降级为阻断，不得静默放行
- 误阻断率控制在 `≤ 10%`
- 对 P0/P1 风险的召回率 `≥ 95%`
- 人工最终决策与模型结果可审计

# 6. 时间与资源估算

以下按“1 名架构师、2 名平台/工具工程师、各系统 0.5～1 名业务开发代表”估算。

| 阶段 | 周期 | 主要产出 | 估算人日 |
|---|---:|---|---:|
| P0 | 2 周 | 资产清单、指标口径、统一配置、基线报告 | 15～20 |
| P1 | 4 周 | 7/7 CI、零欠项门禁、PR 报告 | 30～40 |
| P2 | 5 周 | spec 补齐、Web UI、匹配实测、多模型评审 | 45～60 |
| P3 | 5 周 | Dashboard、线上回灌、治理机制、最终验收 | 35～45 |

# 7. 关键风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 覆盖率口径不一致 | 目标失真 | P0 固化模块清单和计算公式 |
| spec 为了过门禁而低质量补齐 | 文档数量增加但价值不变 | 引入 A/B/C 等级和语义评审 |
| CI 过慢导致团队绕过 | 门禁失效 | PR 快速检查 ≤ 10 分钟，全量检查异步执行 |
| 多模型结论不稳定 | 误阻断或误放行 | 规则模型负责硬门禁，模型只负责语义和风险辅助 |
| 自动映射误判 | 覆盖率虚高 | ERP 等关键系统采用样本集和人工抽样验收 |
| 欠项长期积压 | 质量债务扩大 | owner、截止日期、等级、超期自动升级 |
| 高风险变更绕过评审 | 生产事故 | GitHub Branch Protection 和审计日志双重约束 |
| 线上问题不回灌 | SDD 与实际系统持续漂移 | 缺陷关闭前强制关联 spec 和回归测试 |

# 8. 最终建议

本次升级不应以“新增多少份 `spec.md`”作为主要成果，而应以以下闭环是否真实运行作为判断标准：

```text
每个生产模块都有可执行 spec
每次代码变更都能判断影响范围
每次合并都经过自动门禁
每个欠项都有责任人和期限
每个高风险变更都有评审证据
每个线上缺陷都能回灌到 spec 和测试
每周都能看到质量趋势和退化系统
```

建议将 `P0` 设为不可延期的前置阶段。当前系统数量和覆盖率统计存在口径冲突，在基线未校准前直接推进 80% 或 9/10 目标，会导致最终数据不可审计。完成 P0 后，再以 P1 的全系统门禁接入作为第一个正式交付节点，以 P2 的质量补齐和多模型评审作为核心能力节点，最终在第 16 周完成 9/10 验收。
